04 — AI Agent

How the AI Agent Works

The agent is a multi-step tool-use loop powered by Groq's OpenAI-compatible chat completions endpoint with function calling. It can take up to 8 sequential steps per user message, chaining tool calls to fully satisfy a request.

Agent Loop

1. User sends message ("fix phone numbers in the dataset")
↓
2. System prompt injected (user rules + domain context)
↓
3. Groq returns tool_calls → [ inspect_column("Phone") ]
↓
4. executeTool() runs — returns sample values + missing count
↓
5. Groq sees result → calls apply_rule("Phone", "normalize_phone")
↓
6. executeTool() mutates rows in memory, returns rows_changed count
↓
7. Groq returns final text reply — no more tool calls
↓
8. API responds with { reply, headers, rows, toolLog }

Available Agent Tools

Security — JS Sandbox

The run_transform tool lets the AI write custom JavaScript. Execution is sandboxed by blocking dangerous keywords before new Function() evaluation: 

const blocked = ['require(','import(','process.','__dirname',
  '__filename','eval(','Function(','fetch(','XMLHttpRequest'];

Each expression receives only a single value string — no access to the broader runtime environment.

06 — Data Flow

End-to-End Data Flow

1. Upload / Sample Load

User uploads a CSV or selects a built-in sample. PapaParse runs entirely in the browser — raw data never touches the server until the user triggers a cleansing operation.

2. Profile & Score

Running "Profile Data" computes per-column null %, type distribution, and unique values. A composite Data Quality (DQ) score is computed and displayed as a live gauge.

3. Rules Application (Batch)

"Run Cleanse" applies every active rule in sequence to a copy of the raw data. The result becomes cleanedData — original is preserved for comparison.

4. AI Agent Chat

Each chat message serialises the current dataset (headers + rows) and sends it to /api/agent. The agent mutates a server-side copy; the response returns the full updated dataset which replaces client state.

5. Deduplication

User selects key columns and similarity threshold. Fuzzy matching (Levenshtein distance + token overlap) groups near-duplicate rows and shows a ranked candidate list for review.

6. Export

Clean CSV or audit trail CSV are generated client-side using Papa.unparse and downloaded via an anchor element — no server round-trip needed for export.

07 — Usage

Usage Guide — Tab by Tab

Tab 1 · Upload / Sample

Drag and drop a CSV file or choose one of the three built-in sample datasets (Customer Records, Product Catalog, Address Book). The table preview appears immediately after parsing.

Tab 2 · Rules

Add cleaning rules manually using the form (select column → type → action → optional expression). Or click AI Rules and describe your data in natural language — the AI generates a complete rule set and saves it to your account automatically. Rules can be toggled on/off or deleted at any time.

Tab 3 · Cleanse

Click Run Cleanse to apply all active rules to the dataset in a single pass. The audit log on the right records every transformation with before/after counts.

Tab 4 · AI Chat

Type a natural-language instruction such as: 

"Standardize all country names to their full English form"
"Remove rows where Email is missing"
"Fix the phone numbers — strip country codes and spaces"
"Convert the Revenue column to numbers, remove $ signs"

The agent inspects the data, calls the appropriate tools, and returns the cleaned dataset with a plain-English summary of what it did.

Tab 5 · Profile

Click Profile Data to see: row count, column count, null rate per column, unique value counts, inferred type, and the composite DQ score.

Tab 6 · Dedup

Select which columns define "identity" (e.g. Name + Email), choose Levenshtein or Token similarity algorithm, set the threshold (0–1), and click Find Duplicates. Review matches and remove selected groups.

Tab 7 · Export

Download the clean CSV or the audit trail CSV. The audit CSV records every field changed, original value, new value, rule applied, and timestamp.

Tab 8 · Settings

Set the AI model, configure the domain context (custom instructions injected into every AI prompt), and check the live Groq API status indicator.

Performance Characteristics

Groq Inference Speed

Groq's purpose-built LPU (Language Processing Unit) hardware delivers significantly faster token generation than GPU-based providers. Typical observed performance:

Scalability Notes

Current design (browser-side data): The full dataset is serialized to JSON and sent to the API agent on every chat message. This works well up to ~5,000 rows. For larger files, the Groq API request payload becomes the limiting factor (max_tokens + context window).

Recommended ceiling: ~10,000 rows × 20 columns for the AI agent. Batch rule application (Tab 3) has no AI involvement and scales to 100K+ rows in the browser without issue.

Future scaling path: Upload CSV to Supabase Storage → agent reads paginated chunks via inspect_column → avoids sending full dataset over HTTP.

09 — Security

Security Model

🔑

API Keys — Server Only

GROQ_API_KEY and SUPABASE_SERVICE_ROLE_KEY live in .env.local / Vercel environment variables. They are never exposed to the browser.

🧑‍💻

Authentication — Clerk

Every API route calls auth() from @clerk/nextjs/server. Unauthenticated requests receive HTTP 401 before any data is accessed.

🔒

Row-Level Isolation

All Supabase queries include .eq('user_id', userId). A user cannot read, update, or delete another user's rules — enforced at the API layer.

🏖️

JS Sandbox

AI-generated run_transform expressions are blocked from accessing require, fetch, process, eval, and other dangerous globals.

🚫

Field Whitelist

The PATCH rule endpoint only allows updates to whitelisted fields: field, type, action, expression, description, active. Mass-assignment is impossible.

📡

No Data Persistence

Uploaded CSV data is never written to a database. It exists only in browser memory for the current session and in the request body during agent calls.

11 — Deployment

Deployment & CI/CD

Infrastructure

The application is deployed on Vercel with automatic deployments triggered on every push to the main branch of the GitHub repository. All API routes run as serverless functions (Node.js runtime).

Required Environment Variables

GROQ_API_KEY=gsk_...
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_live_...
CLERK_SECRET_KEY=sk_live_...
NEXT_PUBLIC_SUPABASE_URL=https://xxx.supabase.co
SUPABASE_SERVICE_ROLE_KEY=eyJ...

Supabase Schema

create table rules (
  id          uuid primary key default gen_random_uuid(),
  user_id     text not null,
  field       text not null,
  type        text not null,
  action      text not null default 'custom',
  expression  text,
  description text,
  active      boolean not null default true,
  created_at  timestamptz not null default now()
);
create index rules_user_id_idx on rules (user_id, created_at);

Deploy Steps

Push to GitHub

git push origin main — Vercel detects the push automatically.

Set Env Vars in Vercel

Add the 5 environment variables in Project → Settings → Environment Variables.

Configure Clerk Domain

In Clerk Dashboard → Domains, add the Vercel deployment URL (bare domain, no https://).

Run SQL in Supabase

Execute supabase-setup.sql in the Supabase SQL editor to create the rules table.
